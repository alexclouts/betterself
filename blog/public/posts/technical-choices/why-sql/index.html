Pourquoi une base de données SQL?

Pourquoi une base de données SQL?

Pour stocker les données de BetterSelf, j’ai choisi une base de données relationnelle SQL.

Le choix repose principalement sur la nature des données que l’application devra gérer.

Des données fortement liées entre elles

BetterSelf devra notamment gérer:

  • les utilisateurs;
  • les aliments;
  • les repas;
  • les consommations;
  • les objectifs nutritionnels.

Ces informations sont naturellement liées.

Un utilisateur peut avoir plusieurs repas. Un repas peut contenir plusieurs aliments. Un même aliment peut être consommé plusieurs fois, à différentes dates et dans différents repas.

Une base relationnelle permet de représenter efficacement ces relations.

On peut par exemple imaginer une structure simplifiée comme:

users
  │
  ├── goals
  │
  └── meals
        │
        └── consumptions
              │
              └── foods

Cette structure permet d’éviter de dupliquer inutilement les mêmes informations.

Les requêtes SQL

SQL est également bien adapté aux calculs que BetterSelf devra effectuer.

Par exemple, pour calculer la quantité totale de protéines consommée pendant une journée, le backend pourra interroger les différentes consommations associées à cette journée et effectuer une agrégation.

Ce type de traitement correspond bien au modèle relationnel.

SQLAlchemy

J’utiliserai SQLAlchemy comme couche d’accès à la base de données.

L’utilisation d’un ORM permet de manipuler les données à partir de modèles Python tout en conservant la possibilité d’utiliser les fonctionnalités du système SQL sous-jacent.

Cela devrait également faciliter une éventuelle migration vers une autre base de données relationnelle plus tard.

Pourquoi SQLite au départ?

Pour les premières étapes du développement, je prévois utiliser SQLite.

SQLite a l’avantage d’être très simple à mettre en place puisqu’il s’agit d’une base de données stockée dans un fichier plutôt que d’un serveur de base de données séparé.

Cela réduit considérablement la complexité de l’environnement de développement.

Je peux donc commencer à développer les fonctionnalités de BetterSelf sans devoir configurer immédiatement un serveur PostgreSQL.

Une migration possible vers PostgreSQL

SQLite n’est pas nécessairement le choix final.

Lorsque l’application sera prête à être déployée et utilisée par plusieurs utilisateurs, une base comme PostgreSQL pourrait être plus appropriée.

L’objectif est donc de commencer avec une solution simple pour le développement, tout en conservant une architecture qui permettra éventuellement d’évoluer vers une base de données serveur.

Cette transition devra notamment tenir compte de la persistance des données, des performances, des sauvegardes et de la configuration de l’environnement de production.
