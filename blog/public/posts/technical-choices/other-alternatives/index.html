Quelles alternatives techniques ai-je considérées?

Quelles alternatives techniques ai-je considérées?

Les choix technologiques de BetterSelf ne sont pas apparus spontanément. Plusieurs alternatives ont été considérées avant de retenir l’architecture actuelle.

Frontend: application native Android

Une première possibilité aurait été de développer une application native avec Kotlin.

J’ai déjà travaillé avec Kotlin et Kotlin Multiplatform, ce qui rendait cette approche intéressante.

Cependant, Kotlin Multiplatform ajoute une certaine complexité, notamment lorsque certaines bibliothèques ne sont pas compatibles avec toutes les plateformes ciblées.

Il peut alors être nécessaire de maintenir des implémentations spécifiques pour Android et iOS.

Surtout, BetterSelf doit être conçu comme une application Web dans le cadre du projet scolaire. Une application native ne répondrait donc pas directement à cette exigence.

Frontend: Vue.js

Vue.js constitue une autre alternative intéressante à React.

Les deux technologies permettent de construire des interfaces Web modernes basées sur des composants.

J’ai néanmoins choisi React parce que j’avais déjà un intérêt pour cette technologie et que son écosystème, sa documentation et la quantité de ressources disponibles devraient faciliter mon apprentissage.

Ce choix tient donc autant aux caractéristiques techniques qu’à mon contexte d’apprentissage.

Backend: Node.js

Node.js avec Express ou NestJS aurait permis d’utiliser JavaScript ou TypeScript autant pour le frontend que pour le backend.

Cette approche présente un avantage évident: un seul écosystème de programmation pourrait être utilisé pour l’ensemble de l’application.

Cependant, je suis actuellement plus à l’aise avec Python.

Utiliser Python devrait donc me permettre de consacrer davantage de temps à la logique de l’application plutôt qu’à l’apprentissage d’un nouvel environnement backend.

Backend: Django

Django est une autre solution Python très intéressante.

Il fournit notamment un ORM, un système d’authentification et une interface d’administration.

Son niveau d’abstraction est cependant plus important que ce dont j’ai besoin pour le moment.

FastAPI me paraît mieux adapté à l’approche API séparée que j’envisage pour BetterSelf.

Backend: Flask

Flask est une autre alternative Python légère.

Il est simple et flexible, mais une partie des fonctionnalités dont BetterSelf aura besoin nécessite l’ajout et la configuration de bibliothèques supplémentaires.

FastAPI fournit notamment une validation des données avec Pydantic et une documentation interactive de l’API, ce qui correspond directement à mes besoins.

Base de données: MongoDB

MongoDB pourrait également être utilisé pour stocker les données sous forme de documents.

Cependant, les relations entre les utilisateurs, les repas, les consommations et les aliments correspondent naturellement à un modèle relationnel.

SQL me semble donc plus adapté à la structure actuelle de BetterSelf.

Base de données: PostgreSQL dès le départ

PostgreSQL est également une possibilité tout à fait viable.

J’ai toutefois choisi de commencer avec SQLite afin de réduire la complexité du développement initial.

L’objectif est de pouvoir développer les premières fonctionnalités sans devoir immédiatement administrer un serveur de base de données.

Une migration vers PostgreSQL pourra être envisagée lorsque les besoins de production seront mieux connus.
