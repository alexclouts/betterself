Comment BetterSelf sera-t-il hébergé?

Le choix de l’hébergement n’est pas encore définitif, mais une première architecture se dessine.

L’objectif est de maintenir les coûts aussi bas que possible pendant le développement tout en conservant une architecture qui pourra évoluer si l’application gagne des utilisateurs.

Backend: Railway

Pour le backend FastAPI, Railway est actuellement envisagé comme solution d’hébergement provisoire.

L’un des avantages recherchés est la simplicité du déploiement d’une application Python et la possibilité de travailler avec une architecture conteneurisée.

Le backend pourrait ainsi être empaqueté dans un conteneur Docker et déployé sur la plateforme.

Railway offre également des possibilités d’hébergement de bases de données, ce qui pourrait simplifier l’architecture initiale.

Cependant, les limites du forfait utilisé, les coûts éventuels et les caractéristiques du stockage devront être vérifiés avant un déploiement destiné à de vrais utilisateurs.

Frontend: GitHub Pages

Le frontend React pourrait être hébergé séparément sur GitHub Pages.

Cette approche permettrait de réduire les coûts associés à l’hébergement du frontend puisque celui-ci est constitué principalement de fichiers statiques une fois compilé.

L’architecture serait alors approximativement:

Utilisateur
    │
    ├──────────────► GitHub Pages
    │                 React / PWA
    │
    └──────────────► Railway
                      FastAPI
                         │
                         ▼
                    Base de données

L’inconvénient: deux environnements

Cette architecture introduit toutefois une certaine complexité.

Le frontend et le backend seraient hébergés sur deux plateformes différentes.

Il faudra notamment gérer correctement les communications entre les deux services, les variables de configuration, les politiques CORS et les différentes étapes de déploiement.

Cette séparation devra donc être comparée avec une solution permettant d’héberger davantage de composants au même endroit.

Une décision encore provisoire

Le choix de Railway et GitHub Pages n’est donc pas considéré comme définitif.

Avant le déploiement final, je devrai notamment évaluer:

  • les coûts;
  • la facilité de configuration;
  • la persistance des données;
  • les performances;
  • la facilité de déploiement;
  • les possibilités de migration;
  • la complexité générale de l’architecture.

L’objectif est de trouver un compromis raisonnable entre simplicité, coût et capacité d’évolution.
