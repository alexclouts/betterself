Les technologies choisies

Backend : Pourquoi Python et FastAPI?

Pour l’interface utilisateur, j’ai choisi d’utiliser React, une bibliothèque JavaScript très répandue pour construire des interfaces web interactives. Cette technologie, combinée avec l’approche des PWA, permettra à l’application de se comporter comme s’il s’agissait d’une application native. L’utilisateur pourra donc utiliser ses fonctionnalités à partir de son téléphone cellulaire directement sans avoir à se connecter à une interface Web à chaque fois. Ce choix permet également d’éviter les restrictions imposées par les Apps Store, tels que Google Play, qui ont souvent plusieurs exigences à satisfaire pour que l’application soit accessible.

De plus, l’objectif est que l’application soit également utilisable sur ordinateur (pour les tests, le développement et l’évaluation). Cette technologie est le meilleur des deux mondes. Elle est également très répandue au sein des applications modernes, ce qui rend la documentation exhaustive et facile d’accès.

Backend : Python et FastAPI

Côté backend, j’ai choisi d’utiliser le language Python, couplé au framework FastAPI. D’abord, je suis déjà familié avec la syntaxe de Python pour l’avoir déjà utilisé au sein de projets divers. Je considère que la syntaxe est simple et bien adaptée à ce projet et à ses besoins en terme d’infrastructures. Python est également un language qui intègre bien des fonctionnalités clés de l’application, telles que la gestion des bases de données, l’authentification d’un utilisateur et les appels à des API externes (comme Open Food Facts dans notre cas). Je ne suis pas familier avec FastAPI, mais ce framework a été choisi pour la construction d’un API Web afin d’acheminer les requêtes du frontend au bases de données intégrées. Cette technologie est facile à exécuter localement et à déployer dans un conteneur Docker. J’utiliserai la librairie Pydantic afin de valider les données et les schémas. Mon backend exposera des endpoints via le protocole HTTP afin de transiger les informations demandées par l’utilisateur. Voici des exemples de requête :

GET /api/foods?search=... – rechercher des aliments;
GET /api/foods/by-barcode?barcode=... – obtenir les infos d’un produit via son code-barres;
POST /api/consumptions – enregistrer un aliment consommé;
GET /api/consumptions?date=... – consulter l’historique d’une journée;
GET /api/goals, PUT /api/goals – gérer les objectifs caloriques et protéiques.

Le backend de BetterSelf sera développé avec Python et FastAPI.

Ce choix repose autant sur les besoins du projet que sur mes connaissances actuelles.

Pourquoi Python?

J’ai déjà utilisé Python dans plusieurs projets. Je connais donc déjà sa syntaxe et plusieurs concepts fondamentaux du langage.

Pour ce projet, cette familiarité représente un avantage important. Je pourrai consacrer davantage de temps à la conception de l’application et à l’apprentissage de FastAPI plutôt qu’à l’apprentissage simultané d’un nouveau langage et d’un nouveau framework.

Python dispose également d’un écosystème très développé pour les applications Web, les bases de données et l’utilisation d’API externes.

BetterSelf devra notamment communiquer avec Open Food Facts afin de rechercher des produits alimentaires et de récupérer leurs informations nutritionnelles.

Pourquoi FastAPI?

FastAPI sera utilisé pour créer l’API Web qui servira d’intermédiaire entre React et le backend.

L’architecture sera donc séparée en plusieurs couches:

Utilisateur
    ↓
React / PWA
    ↓ HTTP
FastAPI
    ↓
Logique applicative
    ↓
Base de données

Le frontend ne communiquera donc pas directement avec la base de données.

Cette séparation permet notamment de centraliser la logique métier et les règles de validation dans le backend.

Validation avec Pydantic

FastAPI utilise Pydantic pour définir et valider les données échangées avec l’API.

Cela sera particulièrement utile pour BetterSelf puisque plusieurs types de données devront être transmis entre le frontend et le backend.

Par exemple, lorsqu’un utilisateur enregistre une consommation, le backend devra vérifier que les informations reçues correspondent bien au format attendu.

La validation côté serveur constitue également une protection importante: le frontend ne doit pas être considéré comme une source de données fiable simplement parce qu’il contrôle les champs présentés à l’utilisateur.

Les endpoints prévus

Quelques endpoints envisagés sont:

GET  /api/foods?search=...
GET  /api/foods/by-barcode?barcode=...
POST /api/consumptions
GET  /api/consumptions?date=...
GET  /api/goals
PUT  /api/goals

Cette organisation permet de séparer clairement les différentes responsabilités de l’API.

Par exemple, /api/foods sera associé à la recherche d’aliments tandis que /api/consumptions servira à gérer les aliments effectivement consommés par l’utilisateur.

Pourquoi ne pas utiliser JavaScript également pour le backend?

Une alternative naturelle aurait été d’utiliser Node.js afin d’utiliser JavaScript ou TypeScript autant pour le frontend que pour le backend.

Cette solution aurait l’avantage de réduire le nombre de langages utilisés dans le projet.

Cependant, mes connaissances actuelles en Python sont plus solides que celles que j’ai en Node.js et TypeScript. Le choix de Python devrait donc réduire la courbe d’apprentissage et faciliter le développement et le débogage.

Déploiement

FastAPI se prête également bien à une architecture conteneurisée avec Docker.

Cela permettra de reproduire plus facilement l’environnement de développement sur l’environnement d’hébergement lorsque le projet sera déployé.

Le choix exact de la plateforme d’hébergement demeure toutefois à confirmer.
